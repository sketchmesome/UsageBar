# UsageBar — spec (write ALL code; SwiftPM, macOS 14+, Swift 5.9+, no third-party deps)

Native macOS menu bar app (LSUIElement, no Dock icon). Goal: ~0% idle CPU.
- One `Timer` every settings.refreshIntervalMinutes (default 3 min, clamped 2–30; ~20% tolerance) + refresh on popover open (debounced: skip if last refresh < 60 s ago) + refresh on NSWorkspace.didWakeNotification. NO animations, no spinners, no other timers, no polling loops.
- All file/network work off the main thread; update UI once per refresh.
- NSStatusItem with short text title like "C53 W45" (Codex 5h used %); click opens NSPopover hosting a SwiftUI view. Popover view is destroyed/not rendering when closed.

## Layout
Package.swift (executable target "UsageBar"), Sources/UsageBar/*.swift, Scripts/build_app.sh (swift build -c release, assemble build/UsageBar.app with Info.plist: CFBundleIdentifier com.lanes.usagebar, LSUIElement true, LSMinimumSystemVersion 14.0; ad-hoc codesign `codesign --force -s - `; zip with `ditto -c -k --keepParent` to ~/Downloads/UsageBar.zip).
All app data in ~/Library/Application Support/UsageBar/ (settings.json). Nothing elsewhere.

## Rows (each shows value, source tag LIVE/EST/MANUAL, and "updated X min ago")
1. Codex: primary source is the live account limits read from the local `codex app-server` (SPEC §18). Fallback (offline, or no `codex` on the machine): find newest file under ~/.codex/sessions/**/rollout-*.jsonl (walk only the newest year/month/day dirs, by name sort descending; check at most 3 day-dirs). Read only the last 256 KB of the file, find last line containing `"rate_limits"`, JSON-parse that line, locate the object `rate_limits` anywhere (recursive search) with `primary`/`secondary` each {used_percent, window_minutes, resets_at (unix s)}. Show "5h: X% left (resets HH:mm)", "Week: Y% left (resets EEE HH:mm)". Age = file mtime.
2. Grok Bot: directory ~/Library/Application Support/Grok Bot/sand-client-persistence/. Filenames are lowercase RFC4648 base32 (no padding) + ".blob". Decode each name; pick the one whose decoded name ends with ".weekly-usage.cache". NEVER open any other file there. JSON: {"value":{"reading":{"usage":{"percentUsed":88.1,"nextResetMs":...,"grokPlanLabel":"..."},"readAtMs":...}}}. Show "% left" = 100-percentUsed, reset time, age from readAtMs. If missing, fall back to settings.manualGrokPercentLeft (MANUAL).
3. OpenCode Go: primary source = WKWebView console page URL (settings.opencodeConsoleURL, default "https://opencode.ai/console"; each user pastes their own org URL, e.g. https://opencode.ai/console/org_XXXX/go). Use WKWebsiteDataStore.default() (persisted). "Sign in to OpenCode…" button opens an NSWindow with a visible WKWebView at that URL so the user logs in once; close when done. On refresh: create an offscreen WKWebView (not added to any window or a 1x1 hidden window), load URL, on didFinish wait 4 s (single DispatchQueue asyncAfter), evaluate JS `document.body.innerText`, then DESTROY the webview. Exactly one further read is permitted when that first read carried nothing parseable (no `%`, no `$a / $b` pair, no captured fetch body) — the usual cause is a single-page render that has painted its chrome but not its numbers. No polling loop; the 40 s hard ceiling still applies. Parse text: for labels matching /5[- ]?h(our)?|rolling/i, /week/i, /month/i find nearby percentages (`(\d+(\.\d+)?)\s*%`) or "$a / $b" dollar pairs; produce used% per window. If the page redirects to a login (text contains "sign in"/"log in" and no percentages) mark "needs sign-in". Also add a JS hook: inject WKUserScript at document start that wraps window.fetch and records JSON responses whose URL contains "usage" or "limit" or "go" into window.__ub_json (array, max 20); after load, read JSON.stringify(window.__ub_json) and prefer numeric fields there if found (look for keys containing "used"/"limit"/"percent"). Keep parsing tolerant; show raw short snippet in a debug disclosure if unparsed.
   Fallback (EST): sqlite3 C API (import SQLite3, link "sqlite3") open ~/.local/share/opencode/opencode.db read-only (`file:...?mode=ro` with SQLITE_OPEN_URI|SQLITE_OPEN_READONLY). Query: `select coalesce(sum(json_extract(data,'$.cost')),0) from session_message where json_extract(data,'$.model.providerID')='opencode-go' and time_created > ?` (ms) for 5h, 7d, 30d. Caps from settings.opencodeMonthlyCap (default 80, per opencode.ai/go for DeepSeek V4.1 Flash): 5h=20%, week=50%, month=100%. Show "$spent of $cap (est)".
4. Claude Code: primary source is Anthropic's usage endpoint `GET https://api.anthropic.com/api/oauth/usage` (`Authorization: Bearer <token>`, `anthropic-version: 2023-06-01`, `anthropic-beta: oauth-2025-04-20`), where `<token>` is `claudeAiOauth.accessToken` read from the login Keychain item `Claude Code-credentials` (read rarely — cached until shortly before its expiry; never logged, never persisted). Response `{"five_hour":{"utilization":..,"resets_at":ISO},"seven_day":{...}}`; show "% left" = 100 − utilization. This is the only source that works when Claude Code runs inside the Claude desktop app, which renders no status line. Offline fallbacks, newest written wins: (a) `~/Library/Application Support/UsageBar/claude.json`, written by the terminal status-line hook (tolerate key variants used_percent/utilization); (b) `~/Library/Application Support/Claude/plan-usage-history.json`, written by the desktop app (`samples[{t,org,u:{fh,sd}}]`, where `org` is matched against `oauthAccount.organizationUuid` and never stored). Else show "not connected" + manual fields settings.manualClaude5hLeft / manualClaudeWeekLeft (MANUAL).
5. DeepSeek API balance: STUB. If settings.deepseekEndpointURL and deepseekToken non-empty, GET it with header "Authorization: Bearer <token>", expect DeepSeek's shape {"balance_infos":[{"currency":"USD","total_balance":"12.34"}]}. Else show manual settings.manualDeepseekBalance (MANUAL) or "not set". Never log the token.
6. Spend: monthly prices (Double?) for claude, chatgpt, opencode (default 10), grokbot, vps, other. Total = sum of filled ones; show "$X/mo (n of 6 set)". Empty fields show placeholder "e.g. 20" — never invent values.
7. VPS due: settings.vpsDueDate (Date?), vpsBillingPeriod enum monthly/quarterly/yearly (default monthly). On every refresh and at launch: while dueDate < start of today, advance by one period (Calendar), save. Show "Due in N days (date)"; highlight orange if ≤ 3 days.

## 13. Display currency (all money in one currency, default EUR)
settings.displayCurrency (String, default "EUR"; picker EUR/USD/GBP). Every money value (subscription prices — entered prices are in USD unless settings.priceCurrency says otherwise, default "USD"; VPS price from OVH in GBP; total) is converted to the display currency.
Rates: manual overrides settings.fxOverrides [String: Double] keyed "USD->EUR", "GBP->EUR" etc. win. Else fetch GET https://api.frankfurter.dev/v1/latest?from=EUR (free, no key; JSON {"base":"EUR","date":"..","rates":{"USD":..,"GBP":..}}) and derive cross rates (X->EUR = 1/rates[X]; X->Y via EUR). Fetch at most once per 24 h (also on first launch if no cache), cache with date in ~/Library/Application Support/UsageBar/fx.json. Fallback source https://open.er-api.com/v6/latest/EUR (rates.*). Never hard-code a rate. If a needed rate is unavailable, show that amount in its original currency (total then shows "€X + £Y").
Display: main values in display currency (e.g. "€13.55/mo"); dropdown details keep the original amount, e.g. "€3.47 (orig £3.90 @ 0.8893, ECB 2026-10-14)". Spend row footnote lists each item with original. Settings: display currency picker, price currency picker, manual override fields for USD->EUR and GBP->EUR (blank = auto).
Add menu bar item `totalSpend` (label "Spend", value like "€14"), selectable like the others (not in default set). The DeepSeek balance is a prepaid top-up, so it is NOT converted: the row and menu bar item show it in its own currency (e.g. "$9.89").

## 17. Stale-value flags
Every row carries an optional freshness budget (`UsageRow.staleAfter`). It is the time until the row's tightest usage window resets (`staleBudget(from:resets:)`), so a value is flagged exactly when its window has rolled — an idle hour on a window that has not moved is NOT flagged. `nil` means never stale (manual entries, live fetches). The popover greys a stale value and shows a `STALE` badge plus a ⚠︎ age; `--dump` appends `| STALE`. A reading reused because a fresh fetch failed (OpenCode) is flagged, and the menu bar shows `–` rather than presenting the reused number as current.

## 18. Codex live limits (codex app-server)
Codex's plan limits otherwise only arrive as `x-codex-*` response headers on real API calls, and the Codex *desktop app* writes no local rollout — so a rollout-only source cannot see usage from that surface at all. Primary source: spawn the local `codex` (`~/.local/bin/codex`, else `/opt/homebrew/bin` or `/usr/local/bin`) as `app-server`, send `initialize` → `initialized` → `account/rateLimits/read` as line-delimited JSON-RPC over stdio, read the response for id 2, then kill it. Parse `result.rateLimits.{primary,secondary}` = `{usedPercent, windowDurationMins, resetsAt (unix s)}` plus `planType`; show "% left" = 100 − usedPercent. No model turn is spent, so measuring usage never consumes it. Every wait is bounded (handshake 10 s, response 20 s) so a wedged server cannot hang a refresh; any failure returns nil and the rollout fallback applies. Reads are paced to one per 10 minutes, bypassed by an explicit popover Refresh, which also forces every other paced source (Claude's usage API). `--dump` forces live.

## 19. Faster refresh, live OpenCode estimate, usage alerts
- Main refresh interval range 2–30 min (default 10); timer tolerance = min(120 s, 10% of interval). Codex app-server pacing drops to 100 s; the Claude usage API to 170 s (it rate-limits). On a Claude 429: wait Retry-After (≥ 60 s) or 5 min doubling per consecutive 429 up to 30 min; while waiting keep serving the last snapshot (cache age up to 30 min) and add "Anthropic asked to wait · retry HH:mm" to the row. None of these checks consume model usage.
- OpenCode between console loads: each load records the local DB's rolling Go spend (5h/7d, assistant messages only). Later refreshes read ONE DB snapshot (single connection) and show console used % + (rolling spend now − rolling spend at load) / window cap (cap from the page, else implied by console % and spend at load, else settings cap share; settings.opencodeOverride forces the settings cap share), tagged EST with "est: $x spent since console check". If the newest Go assistant message since the load failed with "usage limit exceeded", 5h is pinned to 0. When gross Go spend recorded since the load reaches $0.50 (or a limit error appears) and the load is ≥ 5 min old, the console is reloaded early. After a failed load (offline/timeout) automatic loads back off 10 min; an explicit Refresh still loads.
- The OpenCode list price (§16) applies only when a plan was identified; no plan → no price.
- settings.usageAlerts (default true): UNUserNotificationCenter alerts per window (Claude/Codex/OpenCode 5h & week, Grok) at 25/10/0% left (once each, re-armed after +5% recovery) and a burn alert when the last 10–45 min of samples project empty within 60 min (≤ 1 per window per 30 min). Burn samples are stamped with the source row's `updated` time, a repeated observation is ignored, and stale or manual (non LIVE/EST) rows are excluded. The first evaluation after launch only seeds state; notification permission is requested only while alerts are enabled. Menu bar % items tint orange ≤ 25%, red ≤ 10% (the tint band is part of the redraw check). Per-price currency pickers cover VPS too.
- OpenCode reset times are parsed from the console ("Resets in 1h 42m" under each window) and shown like the other rows; when a cached load's reset time has passed the console is reloaded.
- Pace: per window, the last 30 min rate (%/h from the alert samples, measured from where use resumed — a leading idle run is trimmed, as it is for burn alerts) vs a learned usual active rate (EMA, fed at most every 15 min, a burst counts at most 2× usual, only trained while the value dropped in the last 10 min, needs 4 feeds; stored as rates only in pace.json). OpenCode pace is $/h from the local DB: last 30 min vs the median of the past 14 days' hours with spend. Every measured row gets one line under its details: the 5h window's rate ("4.2%/h"; "0%/h" when idle, "measuring…" with < 10 min of readings; a single-window source uses its only window; DeepSeek in $/h), then the weekly burn "9%/day · lasts until reset" / "· runs out in ~2 days, before reset" (used ÷ days since the week began, fresh readings only; nothing in the first 6 h). The learned usual is not displayed; it only drives alerts. OpenCode's $/h DB pace likewise only drives its alert; ≥ 2× usual (and ≥ 3 %/h or ≥ $0.25/h) sends a "Slow down" notification, at most hourly per window.
- Popover footer shows "Sign in to OpenCode…" only when the OpenCode row says "needs sign-in", else "Open OpenCode console…".
- Review round (v1.2): pace history splits at breaks anywhere (a no-decline run or observation gap ≥ max(15 min, 1.5× refresh interval)); pace/history spans scale with the refresh interval; pace-alert cooldowns persist in pace-alerts.json; persisted future timestamps are clamped to now. OpenCode resets accept "2 hours 59 minutes" style and "0m" (imminent → reload next tick); console freshness ends at the earliest reset; DB "recent" queries ignore future-dated rows. Claude: an explicit Refresh only overrides newer local data with a snapshot fetched in that call; Retry-After accepts HTTP-dates and is anchored at the response; the "Anthropic asked to wait" note is added to whichever source ends up on the row.

## 20. DeepSeek pace, runway and VPS disk trend
- Pace notes always show the raw rate: "pace 4.2%/h (1.3× usual)", or "pace 4.2%/h" while learning.
- The DeepSeek balance (live only) is a pace window in its own currency: "$/h" pace notes, burn and "Slow down" alerts (min active $0.01/h, alert ≥ $0.25/h, burn ≥ $0.25 drop); any rise is a top-up and restarts its history. No % thresholds.
- Trends.swift keeps hourly samples (values only) of the DeepSeek balance and VPS disk used GB for 30 days in trends.json. DeepSeek: daily spend = sum of drops over the last 7 days (top-ups skipped) / days covered (needs ≥ 20 h); row note "≈ N days left at $x/day"; notification when < 3 days. Disk: growth GB/day since the last cleanup (> 0.5 GB drop) over ≤ 7 days (needs ≥ 20 h); VPS Disk line shows "+x GB/day · fills in ~N days" (or "steady" under 0.02 GB/day); notification when < 14 days. Each warning at most once a day (persisted; nothing recorded while alerts are off). Every refresh is observed: drops between saved samples accumulate into the next sample (`d`), a cleanup in between marks it (`c`); that in-between state is persisted whenever the value moves (a drop, a top-up, growth), so a restart within the hour keeps it; the DeepSeek series restarts if its currency changes; all series are pruned to 30 days (and future-dated samples dropped) on every update. Growth without free-space data shows "+x GB/day" without a fill date. Pace history/training/cooldowns are repaired when the clock is set back; the DeepSeek pace window is keyed by currency.
- Pace history (recent readings per window, ≤ 1 h) is saved to pace-history.json after each refresh that added a reading and reloaded at launch, so pace survives restarts/updates. While a window is in use but has < 10 min of readings, its note is "pace: measuring…". The DeepSeek row footnote shows DeepSeek's split ("$9.13 topped up + $0.73 granted") while the value stays the total.
